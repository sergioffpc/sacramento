# C++ Engineering Toolchain and Quality Guidance

Status: Research guidance

Research date: 2026-09-01

Purpose: Recommend a C++ engineering baseline for correctness, portability,
diagnosability, measured performance, and repeatable builds of the Training
Simulation and Simulation Engine.

Scope: Language policy, compilers, code conventions, build and dependency
tooling, tests, benchmarks, fuzzing, analysis, hardening, CI, and reproducibility.

Prerequisites: [Training Simulation context](../../CONTEXT.md),
[initial requirements](../requirements/training-simulation-initial-requirements.md),
[non-functional requirements](../requirements/training-simulation-non-functional-requirements.md),
[reference hardware profiles](../requirements/training-simulation-reference-hardware-profiles.md),
and [verification plan](../requirements/training-simulation-verification-plan.md).

Canonical information owner: None. This research is not an approved architecture,
style profile, toolchain profile, or verification baseline.

Decision outcome: This research informed the approved
[C++ Engineering Baseline](../standards/cpp-engineering.md). Where this note's
candidate recommendations differ from that baseline, the approved baseline is
authoritative. In particular, the project selected Clang as its only C++
compiler and rejected the candidate MSVC and GCC validation lanes.

## Executive recommendation

Adopt the following candidate stack, then pin exact versions after a small
cross-platform proof build:

| Concern | Recommendation |
| --- | --- |
| Build | Modern target-based CMake, executed by Ninja, with checked-in CMake presets |
| Dependencies | vcpkg manifest mode, pinned vcpkg commit and baseline, project triplets, controlled source/binary cache |
| Windows | clang-cl development, release, and acceptance build; MSVC independent validation build |
| Linux | Clang development, release, and acceptance build on Debian; GCC independent validation build |
| Format/lint | One pinned LLVM distribution supplying clang-format, clang-tidy, clangd, llvm-cov, and symbolizer |
| Tests | GoogleTest/GoogleMock registered in CTest |
| Benchmarks | Google Benchmark plus system performance tests on the approved profiles |
| Fuzzing | libFuzzer with ASan and UBSan, persisted corpora and minimized regressions |
| Static analysis | Compiler warnings and clang-tidy on changes; full clang-tidy and CodeQL on merge/schedule |
| Dynamic analysis | ASan+UBSan, separate TSan, and an MSan lane only with a fully instrumented dependency graph |

CMake directly models C++23, shared presets, CTest, and Clang compilation
databases. Ninja is explicitly designed as a fast executor generated by a
higher-level build system. vcpkg manifest mode isolates project dependencies and
enables versioning and custom registries. [CMake standard properties](https://cmake.org/cmake/help/latest/prop_tgt/CXX_STANDARD.html),
[CMake presets](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html),
[Ninja manual](https://ninja-build.org/manual.html),
[vcpkg manifest mode](https://learn.microsoft.com/en-us/vcpkg/concepts/manifest-mode)

This stack does not select a renderer, physics, audio, networking, ECS, or whole
game engine. Those choices need architecture evidence against the requirements.

## Project constraints

The repository is still defining requirements and has no production architecture.
The approved baseline already fixes the decisions that generic C++ advice must
not override:

- standard C++23, with no later language mode or non-standard extension
  (`CONSTRAINT-CPP-VERSION-001`);
- 64-bit Windows 11 clients and a Debian 13 amd64 Session Authority, with shared
  Simulation Engine Platform Parity preferred (`CONSTRAINT-PLATFORM-MATRIX-001`);
- a self-contained Project C++ Style Profile substantially based on the Google
  guide, with exact deviations and review duties (`CONSTRAINT-CPP-STYLE-001`);
- pinned clang-format, clang-tidy, compiler warning profiles, versions, and local/CI
  invocations, with zero unexplained diagnostics (`CONSTRAINT-CPP-FORMAT-001`
  through `PROCESS-CPP-STYLE-GATE-001`);
- authoritative canonical state, deterministic acceptance replays, exact build
  identity, and obligation-level verification, so coverage alone is not evidence
  of correctness;
- measured 16.67 ms final-image and 100 ms stall limits on exact reference
  profiles; and
- no more than two concurrently assigned human generalists.

These constraints favor one conventional cross-platform build definition and
extensive automation over custom infrastructure or platform-specific projects.

## Toolchain and language

### Compiler matrix

| Lane | Purpose |
| --- | --- |
| Windows/clang-cl | Primary client development, release and acceptance, Windows SDK/MSVC ABI, warnings-as-errors, tests, selected ASan tests |
| Windows/MSVC | Independent mandatory validation of Windows conformance, SDK/ABI integration, warnings-as-errors, and tests |
| Debian/Clang | Primary Session Authority development, release and acceptance, warnings-as-errors, hardening, clang-tidy, ASan+UBSan, coverage, and fuzzers |
| Debian/GCC | Independent mandatory validation of Linux portability, warnings-as-errors, hardening, and tests |
| Debian/Clang TSan | Separate representative concurrency tests |
| Controlled Clang MSan | Scheduled uninitialized-read checks when all linked code is instrumented |

This is a **Clang-first, native-compiler-verified** policy. It makes one LLVM
frontend and tool family the daily path on both platforms without pretending the
complete toolchains are identical: clang-cl still uses the Windows SDK, MSVC ABI,
CRT and normally the MSVC standard library, while Clang on Debian normally uses
the platform linker and libstdc++. Pin those platform components too. MSVC and
GCC remain blocking validation lanes because an independent frontend detects
portability defects and accidental compiler dependencies that Clang alone cannot.
Do not assume any compiler has better runtime performance; compare the Clang,
MSVC, and GCC outputs on the approved workloads and reference hardware.

Pin compiler, standard library, linker, SDK/sysroot, CMake, Ninja, LLVM tools,
vcpkg commit, triplets, and relevant environment as one toolchain profile. A
compiler version alone is not reproducible.

Do not assume that selecting a C++23 flag proves support. GCC, Clang, and MSVC
publish feature-by-feature conformance status, and Clang currently describes its
overall C++23 implementation as partial. Compile a repository feature probe for
every C++23 facility admitted by the project and use only the intersection of all
mandatory compiler lanes and their standard libraries. [GCC C++ status](https://gcc.gnu.org/projects/cxx-status.html),
[Clang C++ status](https://clang.llvm.org/cxx_status),
[MSVC conformance](https://learn.microsoft.com/en-us/cpp/overview/visual-cpp-language-conformance)

Require C++23 mechanically on every first-party target:

```cmake
target_compile_features(sacramento_engine PUBLIC cxx_std_23)
set_target_properties(sacramento_engine PROPERTIES
  CXX_STANDARD 23
  CXX_STANDARD_REQUIRED YES
  CXX_EXTENSIONS NO)
```

`CXX_STANDARD_REQUIRED` prevents silent decay to an older standard and
`CXX_EXTENSIONS NO` selects the non-vendor dialect. Use `-std=c++23`, not
`gnu++23`; on MSVC use `/permissive-`, `/Zc:__cplusplus`, and the applicable
`/Zc:*` conformance switches. Never use a latest/post-C++23 mode.
[CMake requirements](https://cmake.org/cmake/help/latest/prop_tgt/CXX_STANDARD_REQUIRED.html),
[CMake extensions](https://cmake.org/cmake/help/latest/prop_tgt/CXX_EXTENSIONS.html),
[MSVC conformance switches](https://learn.microsoft.com/en-us/cpp/build/reference/zc-conformance)

There is a current MSVC/CMake integration risk that the proof build must close.
MSVC Build Tools 14.51 still offers `/std:c++23preview`, not a stable
`/std:c++23`; Microsoft states that this mode enables only C++23 features but may
change ABI between tool releases. `/std:c++latest` also enables post-C++23 and
experimental work and therefore does not satisfy `CONSTRAINT-CPP-VERSION-001`.
Moreover, CMake's `cxx_std_23` selection can currently emit `/std:c++latest` for
MSVC. The MSVC validation profile must consequently pin one MSVC release, force
`/std:c++23preview` after CMake's standard option when necessary, and verify the
effective compiler command and `_MSVC_LANG`; all linked first-party code must use
the same pinned toolset. Replace the preview switch with stable `/std:c++23` when
Microsoft supplies it. Do not approve the MSVC validation profile until its
probe proves these conditions.
[MSVC language modes](https://learn.microsoft.com/en-us/cpp/build/reference/std-specify-language-standard-version),
[MSVC Build Tools 14.51](https://learn.microsoft.com/en-us/cpp/overview/what-s-new-for-msvc),
[CMake's current MSVC C++23 limitation](https://discourse.cmake.org/t/visual-studio-select-std-c-23preview-or-std-c-latest/15456)

Delay C++ modules. LLVM's libc++ documentation still describes module support as
experimental and binary module interfaces as compiler-configuration dependent.
Use self-contained headers; evaluate PCH or unity builds only as measured local
accelerators, while retaining a clean non-unity CI build.
[libc++ modules](https://libcxx.llvm.org/Modules.html)

### Portability and deterministic behavior

Require explicit units and clocks, encodings, serialization widths and byte order.
Never serialize object layout, padding, pointers, native enum representation, or
unordered-container iteration. Hide OS APIs and compiler attributes behind narrow
adapters with standard public interfaces.

Separate three properties and test each:

1. logical determinism: identical admitted inputs, seed, state, and event order
   yield identical canonical outcomes;
2. stable serialization: canonical values have one versioned representation
   independent of padding, bucket order, address, locale, and platform;
3. reproducible build: identical source and pinned environment yield identical
   artifacts.

Do not claim cross-compiler bitwise floating-point determinism without a dedicated
profile. Canonical simulation needs stable reduction/iteration order, controlled
random algorithms and seeds, explicit quantization/tolerances, and no outcome
dependence on thread scheduling. Prohibit `-ffast-math` and equivalents in
canonical state, physics, ballistics, scoring, timing, and validation. GCC
documents that this flag enables relaxed assumptions such as finite-only math.
[GCC optimization options](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)

## Code and API policy

Create a repository-owned style profile with this precedence: approved Sacramento
requirements and vocabulary; explicit Sacramento rules/deviations; adopted Google
rules; selected C++ Core Guidelines; formatter output. The live Google guide
changes and currently targets C++20, so it cannot itself be normative here.
[Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)

Recommended semantic rules:

- prefer values, immutability, RAII, and Rule of Zero;
- raw pointers/references are non-owning; use `unique_ptr` for exclusive ownership
  and `shared_ptr` only for genuinely shared lifetime;
- make invalid states unrepresentable using domain value types, closed enums,
  validated factories, and explicit transitions;
- use `span` and `string_view` only within the owner's proven lifetime;
- use `nodiscard` for ignorable error/state/resource results and `noexcept` only
  where the complete call chain guarantees it;
- use `std::expected` or a project result type for expected runtime and validation
  failures; assertions represent programmer invariants, not hostile input;
- no exception crosses a thread entry, C ABI, plugin, process, or subsystem
  boundary; decide internal exception use in an ADR rather than blindly copying
  Google's ban, whose own rationale is tied to Google's legacy codebase;
- minimize shared writable state, bind mutexes to protected data, use scoped locks,
  and never use `volatile` for synchronization;
- instrument allocations and assign budgets to measured frame/tick/audio paths;
  do not impose a global allocation ban;
- public APIs state ownership, lifetime, units, ordering, thread-safety, blocking,
  and failure, and do not expose third-party concrete types.

The Core Guidelines explicitly promote RAII, visible ownership, minimized mutable
sharing, scoped locks, tool-assisted concurrency validation, and measured rather
than assumed performance. [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines.html)

Store every clang-format option explicitly and reject any change the exact pinned
formatter would make. clang-format supports repository YAML configuration and a
Google base style. [clang-format options](https://clang.llvm.org/docs/ClangFormatStyleOptions.html)

## Build and dependencies

Use modern target-based CMake: one cohesive module per target; explicit
`PRIVATE`/`PUBLIC`/`INTERFACE` requirements; no directory-global include paths,
definitions, or warning flags; explicit source lists; generated files only in the
build tree; first-party warning/hardening interface targets; and tests linking the
same production libraries. Generate `compile_commands.json` for Clang tools.

Check in `CMakePresets.json` with configure/build/test/workflow presets and ignore
developer-only `CMakeUserPresets.json`, exactly as CMake documents.
[CMake presets](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html)

CMake+Ninja is lower risk than the alternatives:

- Bazel has valuable hermeticity, remote cache, and remote execution, but adds
  substantial toolchain/rule ownership for two generalists. Reconsider if scale
  makes those properties a measured need. [Bazel hermeticity](https://bazel.build/concepts/hermeticity)
- Meson is concise and also uses Ninja, but offers no demonstrated project benefit
  sufficient to outweigh CMake's package, IDE, test, and engine-library ecosystem.
  [Meson](https://mesonbuild.com/)
- direct MSBuild cannot be the single source for the Linux Session Authority;
  handwritten Ninja contradicts Ninja's intended generated-backend role.

Use one package manager. vcpkg fits this Windows/Linux, CMake-centered project;
Conan 2 is the strongest alternative if custom binary-package ABI matrices and a
private package factory dominate. Decide in an ADR after a proof using one real
dependency graph. [Conan profiles and CMake](https://docs.conan.io/2/tutorial/consuming_packages/build_simple_cmake_project.html)

For vcpkg, commit manifest/configuration, pin repository commit and baseline,
record triplets and overrides, and retain the resolved direct/transitive graph,
source hashes, licenses, features, ABI options, vulnerability disposition, and
cache provenance. vcpkg warns that its extensive ABI hash can still be defeated
by nondeterminism. [vcpkg versioning](https://learn.microsoft.com/en-us/vcpkg/users/versioning),
[binary-cache ABI hash](https://learn.microsoft.com/en-us/vcpkg/reference/binarycaching)

Release and acceptance builds must not perform floating network downloads.
Prepopulate a controlled source cache/registry and fail if material is missing.
Use CMake FetchContent only for small pinned development/test dependencies, not as
an unreviewed second package manager. [CMake dependency guide](https://cmake.org/cmake/help/latest/guide/using-dependencies/index.html)

## Testing and performance

Use GoogleTest/GoogleMock with CTest. GoogleTest targets independent, repeatable,
portable tests; CTest supplies one preset-driven runner and non-zero failure
status. [GoogleTest primer](https://google.github.io/googletest/primer.html),
[CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

Maintain separate suites for unit algorithms/invariants, component APIs,
integration and failure injection, determinism/golden state, schema compatibility
and rejection, and exact system acceptance. Prefer behavior-rich fakes over mocks
of private call order.

Use Clang source-based coverage to locate gaps; it reports function,
instantiation, line, region, and branch coverage. A percentage is not correctness
or obligation-level verification. [Clang coverage](https://clang.llvm.org/docs/SourceBasedCodeCoverage.html)

Fuzz every untrusted byte boundary: network framing/messages; Map, Scenario,
profile, catalogue and identity packages; serialization/version rejection;
authentication/audit state machines; action sequences; and third-party asset
decoders. Run libFuzzer with ASan+UBSan, bounded inputs, dictionaries, checked-in
minimal corpora, and permanent regression seeds. [libFuzzer](https://llvm.org/docs/LibFuzzer.html)

Use Google Benchmark for algorithms and allocators, with repetitions and JSON
evidence, but retain the approved five-minute workload as the performance gate.
Google Benchmark reports distribution statistics and supports counters,
multithreading, and profiling hooks. [Google Benchmark](https://google.github.io/benchmark/user_guide.html)

Profile before optimizing. Use WPR/WPA for ETW CPU/system traces and NVIDIA Nsight
Graphics GPU Trace on the reference client, and Linux `perf stat`/`perf record`
on the Session Authority. Enable ThinLTO or PGO only after before/after
correctness and workload evidence; Clang warns that unrepresentative PGO inputs
can cause poor optimization. [Windows Performance Toolkit](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/),
[Nsight Graphics](https://docs.nvidia.com/nsight-graphics/),
[Linux perf documentation](https://github.com/torvalds/linux/tree/master/tools/perf/Documentation),
[Clang PGO](https://clang.llvm.org/docs/UsersManual.html#profile-guided-optimization),
[ThinLTO](https://clang.llvm.org/docs/ThinLTO.html)

## Analysis, sanitizers, and hardening

Treat warnings as errors only for first-party targets: `/W4 /WX /permissive-` on
MSVC and a pinned profile beginning with `-Wall -Wextra -Wpedantic -Werror` on
GCC/Clang. Do not enable Clang `-Weverything` or warning-as-error for third-party
code. GCC documents the exact warning-group and pedantic behavior.
[GCC warning options](https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html)

Use an explicit reviewed `.clang-tidy` list: selected `clang-analyzer-*`,
`bugprone-*`, `cert-*`, `concurrency-*`, `performance-*`, `portability-*`,
`readability-*`, and enforceable adopted `cppcoreguidelines-*`/`google-*` checks.
Set admitted diagnostics as errors, validate the configuration, run affected
translation units on PRs and the whole project later. LLVM warns that diff-only
filtering can miss diagnostics emitted elsewhere. [clang-tidy](https://clang.llvm.org/extra/clang-tidy/)

Run CodeQL with an explicit CMake build so it observes the real compilation
configuration and generated sources. GitHub documents manual, autobuild, and
no-build modes for C/C++; use manual mode for the authoritative configuration.
Availability depends on repository visibility and GitHub licensing.
[CodeQL compiled-language builds](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages)

Adopt Clang thread-safety annotations behind portable project macros for shared
state. This compile-time analysis has no runtime overhead and complements TSan.
[Thread Safety Analysis](https://clang.llvm.org/docs/ThreadSafetyAnalysis.html)

Sanitizer plan:

- ASan+UBSan on every Linux PR and representative scheduled integration runs;
- TSan separately, because of incompatible instrumentation and its documented
  5x-15x time and 5x-10x memory overhead;
- MSan only with instrumented standard library and dependencies;
- LSan with ASan where supported;
- no sanitizer runtime in production: LLVM explicitly warns that ASan is not a
  production security runtime.

[ASan](https://clang.llvm.org/docs/AddressSanitizer.html),
[UBSan](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html),
[TSan](https://clang.llvm.org/docs/ThreadSanitizer.html),
[MSan](https://clang.llvm.org/docs/MemorySanitizer.html)

For the clang-cl release, retain `/GS`, enable and verify `/guard:cf` plus linker
`/GUARD:CF` and required `/DYNAMICBASE`. For the Debian Clang release, define and
benchmark an explicit profile beginning with `-fstack-protector-strong` and the
applicable linker and libc hardening options. Keep an independently verified GCC
`-fhardened` profile for comparison. Verify mitigations on the final binary
rather than accepting configuration flags as evidence.
[Clang-cl options](https://clang.llvm.org/docs/UsersManual.html#clang-cl),
[Clang command-line reference](https://clang.llvm.org/docs/ClangCommandLineReference.html),
[MSVC Control Flow Guard](https://learn.microsoft.com/en-us/cpp/build/reference/guard-enable-control-flow-guard),
[GCC hardening](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html)

## CI and reproducibility

Use GitHub Actions as a thin orchestrator calling the same checked-in presets and
scripts as local development. Use matrices for compiler/OS combinations. Pin
every action to a full commit SHA and grant minimum explicit permissions; GitHub
states that a full SHA is the only immutable action reference.
[Actions matrices](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs),
[secure use](https://docs.github.com/en/actions/reference/security/secure-use)

For reproducibility, pin every input, normalize locale/timezone/archive order/file
permissions, prohibit wall-clock timestamps/random IDs/hostnames/absolute paths,
use `SOURCE_DATE_EPOCH`, and map source/build roots out of debug and macro paths.
The SOURCE_DATE_EPOCH specification defines a source-derived deterministic
timestamp; GCC documents `-ffile-prefix-map` for location-independent builds.
[SOURCE_DATE_EPOCH](https://reproducible-builds.org/specs/source-date-epoch/),
[GCC prefix maps](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)

Build each release twice in fresh isolated workspaces and compare hashes, then
structurally investigate differences. Define reproducibility per exact platform
and toolchain; Windows and Linux binaries need not match each other.

Publish the resolved dependency graph and enable dependency/vulnerability review.
GitHub's dependency review can block pull requests introducing dependencies at a
configured severity. [Dependency review](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/configure-dependency-review-action)

## Quality gates

| Gate | Blocking checks |
| --- | --- |
| Pre-push | Format; configure; warnings-as-errors build; affected tests and clang-tidy units |
| Pull request | Primary clang-cl and Clang builds plus mandatory MSVC and GCC validation builds; tests; ASan+UBSan; dependency/license review; affected determinism/serialization tests |
| Merge/nightly | Full clang-tidy; CodeQL when available; TSan; feasible MSan; coverage; bounded fuzzing; clean non-unity builds; repeated determinism; benchmark trends |
| Release candidate | Exact clang-cl Windows and Clang Debian release builds; MSVC/GCC validation; hardening verification; regression corpora; two reproducible builds per platform; vulnerability/license disposition; provenance |
| Formal acceptance | Exact admitted hardware/OS/drivers/build/configuration/content/workload; production-parity observability; every required method and obligation-level disposition |

No warning suppression, sanitizer ignore, disabled test, or fuzz exception should
merge without the repository's approved exception record, owner, and expiry.

## Adoption and open decisions

1. Approve an ADR for CMake+Ninja and choose vcpkg versus Conan after a proof.
2. Build a minimal shared library, clang-cl Windows client, Clang Linux authority,
   and GoogleTest executable; run the same code under MSVC and GCC, execute the
   C++23 feature probe, and pin every complete toolchain.
3. Approve the self-contained Project C++ Style Profile and generated formatter,
   linter, warning, and exception inventories.
4. Add presets for dev, release, ASan+UBSan, TSan, coverage, fuzz, and acceptance.
5. Establish determinism, serialization, fuzz, and performance baselines before
   feature volume grows.
6. Add full static analysis, reproducibility, hardening, dependency review, and
   provenance before the first release candidate.

Still requiring explicit architecture/owner decisions: exact tool versions and
C++23 feature subset; exceptions and RTTI; floating-point/random/concurrency
determinism; renderer, physics, audio, networking, serialization, and crypto;
plugin ABI; exact warning/tidy lists; performance thresholds; signing,
attestations, and SBOM format.
